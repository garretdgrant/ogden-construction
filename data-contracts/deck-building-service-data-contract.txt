## Custom section shape

Use `customSections` when useful content does not fit a named section. Custom sections may be added, removed, ordered, and titled freely.

```ts
const {camelCaseSlug}CustomSections: ServiceDetailCustomSection[] = [
  {
    id: "unique-kebab-case-anchor",
    eyebrow: "Optional section context",
    title: "Visible H2",
    description: "Optional section introduction",
    surface: "default",
    placement: "before-faqs",
    blocks: [],
  },
];
```

Allowed surfaces:

```txt
default | muted | contrast
```

Allowed placements:

```txt
after-overview | before-faqs | before-contact
```

Use only these custom-section blocks:

```ts
{ type: "paragraph", text: "Plain text only." }
{ type: "heading", text: "Visible H3" }
{ type: "unordered-list", items: ["Plain-text item"] }
```

## Contract rules

- Use `kind: "service"`, `template: "service-detail"`, and a route under `/services/{slug}`.
- `slug`, `pageHref`, `metadata.canonicalPath`, breadcrumbs, export name, and output filename must describe the same service and route.
- Set `dateModified` to the real date the generated file is produced. Do not use a future date or a research publication date.
- `hero.title` is the page's only H1. Named-section and custom-section titles render as H2s. Custom `heading` blocks render as H3s.
- The named content sections are optional. Omit an entire named property when it does not improve the page or the supplied research does not support it.
- There is no fixed section count, custom-section count, word count, FAQ count, or required outline. Add only sections that improve search intent, topical completeness, readability, or conversion.
- Use custom sections for genuinely distinct content. Do not repeat material already covered by overview, service types, choices, capabilities, planning factors, process, scope, projects, locations, resources, or FAQs.
- Every rendered section needs a unique kebab-case `id`. Every custom section needs at least one supported block.
- Add anchor navigation when useful. Every anchor `href` must exactly match a named section ID, custom section ID, `#frequently-asked-questions`, or `#contact`.
- Keep anchor links in the same order the sections render on the page.
- Choose section surfaces for page rhythm and readability. Use `contrast` sparingly and avoid placing several sections with visually similar surfaces together when another supported surface improves the flow.
- Use the supplied service research to define `pageOwns`, `pageDoesNotOwn`, and supporting topics. Do not make one service page own unrelated services, informational guides, or every city-specific variation.
- Keep city-specific commercial intent on the corresponding location pages unless the supplied SEO plan explicitly says otherwise.
- Link naturally to verified service, location, portfolio, guide, and contact routes. Do not guess internal slugs.
- Use only verified image paths and real image dimensions. Do not reuse an unrelated image or claim an image shows an Ogden Construction project unless verified.
- Use projects only when the title, location, scope, materials, and link are supplied or verifiable in project files.
- The shared `OgdenFaqSection` renders FAQs with visible HTML content. Add FAQs only when they answer useful service-specific questions rather than repeating section headings.
- Set `structuredData.schemaType` to `Service`. The existing JSON-LD builder derives Service, WebPage, ImageObject, BreadcrumbList, and optional FAQPage schema from this data. Do not embed raw schema in the data file.
- Set `includeFaqSchema` to `true` only when the file contains useful FAQs. Set `includeBreadcrumbSchema` to `true` when valid breadcrumbs are supplied.
- The current lead-form renderer preserves the standard name, email, phone, and project-details form behavior. The additional lead-form planning fields are reserved data and do not create extra form inputs.
- Text fields render as plain text. Do not use HTML, JSX, Markdown formatting, Markdown links, or escaped markup.
- Write in natural American English at roughly a 7th- to 9th-grade reading level.
- Avoid filler, doorway-page copy, repetitive keyword variations, generic sales claims, and sections added only to increase page length.
- Do not invent prices, timelines, warranties, guarantees, financing, product certifications, manufacturer status, permit outcomes, engineering requirements, code conclusions, availability, response times, testimonials, ratings, awards, project counts, customer counts, or completed-project locations.
- Keep climate, terrain, drainage, snow, heat, access, plans, permits, engineering, and inspection statements practical and qualified rather than presenting them as universal requirements or professional engineering advice.
- Before returning the file, confirm that it satisfies `ServiceDetailPageData`, uses only supported custom blocks, contains no duplicate object keys, has valid anchors and routes, and can render without component changes.
